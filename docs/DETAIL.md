# SDD-компас

Плагин показывает, где проект находится в SDD-процессе: фазу активного
изменения, прогресс задач, замечания и документы, которые стоит прочитать.
Он не заменяет OpenSpec или другой процесс — он читает их артефакты и
превращает их в компас.

## Что видно

Строка под полем ввода: `SDD ● реализация 4/7 ⚠2`. Точка зелёная у
завершённого изменения, жёлтая у работы в процессе, серая без изменений,
красная при ошибке. Клик открывает панель с тремя вкладками.

**Статус.** Лестница фаз `проект → предложение → спека → дизайн → задачи →
реализация → проверка → архив`, артефакты, задачи, следующий шаг, замечания и
документы.

**Статистика.** Дни в текущей фазе, число изменений в работе, застрявшие
изменения, задачи, а из git — медиана и p90 цикла «спека → архив», доля
дошедших до архива изменений и дрейф за 7 дней. Без git история честно
показывает «мало данных».

**Документы.** Не больше пяти ссылок с причиной: артефакт изменения, правила
проекта, глоссарий, документация, спека проекта.

## Как вычисляется фаза

Фаза не хранится: она функция от файлов на диске.

- **OpenSpec:** proposal → specs → design → tasks; затем незакрытые задачи —
  `реализация`, все закрыты — `проверка`, каталог в `changes/archive/` —
  `завершено`.
- **Scratch:** `spec.md`, затем `issues/NN-*.md`; статусы `done`/`wontfix`
  закрывают задачу, `in-progress`/`review`/`blocked` означают работу,
  `ready-for-agent` — ещё не начатую.
- **SSC:** `model.json` (корень или `docs/*/model.json`). Фаза `спека`, пока
  есть несогласованные артефакты (`needs_review`), статус `draft`/`needs_review`
  или блокирующие открытые вопросы; при согласованной модели и без блокеров —
  `проверка`. Строка «Следующее действие» из `workflow.md` показывается в
  статусе как ориентир анализа.

## Замечания

- изменение не обновлялось дольше `staleAfterDays` (по умолчанию 14);
- задачи выполнены, но изменение не заархивировано дольше 7 дней;
- правки кода в рабочем дереве или коммиты за 7 дней при фазе предложения,
  спеки или дизайна — дрейф «код раньше спеки»;
- у scratch-задач статусы не двигаются или закрытые тикеты не имеют отмеченных
  пунктов;
- у OpenSpec есть готовые изменения, но `changes/archive/` пуст;
- у SSC есть несогласованные артефакты (`ssc.review`), блокирующие вопросы
  (`ssc.blockers`) или сломанный `model.json`.

Замечания ничего не блокируют. Жёсткий режим включается в `.sdd/config.json`:
`strictness: "gate"` — тогда запись кода вне артефактов в фазе предложения,
спеки или дизайна отклоняется с причиной.

## Строгость

| значение | поведение |
|---|---|
| `quiet` | только строка и `/sdd` |
| `info` | + секция промпта и брифинг в начале сессии |
| `warn` (по умолчанию) | + предупреждение модели после записи кода в фазе спеки |
| `gate` | + запрет записи кода до утверждения спеки |

## Документы

Плагин собирает индекс документации: артефакты активного изменения, правила
проекта (`AGENTS.md`, `GLOSSARY.md`, `README.md`), документацию из
`docs.roots` и спеки проекта. Документы, совпавшие с модулями изменённых
файлов, помечаются как «документация изменённого модуля» и поднимаются выше
в списке.

## Аннотации @sdd

Код и тесты можно связать со спекой аннотацией:

```ts
// @sdd FR-012                         — требование SSC
// @sdd composition-contour-and-fields — изменение OpenSpec
```

Сканер читает только каталоги из `trace.roots` (по умолчанию `src`, `app`,
`lib`, `tests`, `test`, `packages`), не больше `trace.maxFiles` файлов, и
кеширует индекс на 10 минут. Замечания:

- `trace.unknown` — аннотация ссылается на несуществующий ID;
- `trace.orphan` — у требований SSC нет ни одной аннотации;
- `trace.unannotated` — изменённый код без аннотаций в фазе реализации или
  проверки.

Покрытие видно в статистике: `аннотации @sdd: N файл(ов) · требования X/Y`.

## Портфель

`/sdd projects` и вкладка «Проекты» в панели показывают сводку по проектам из
workspace-реестра: практика, фаза, активное изменение и число предупреждений.
Модели доступен инструмент `sdd_projects`.

## Следующий шаг

`/sdd advance` печатает точную команду шага (например,
`openspec archive --change <имя>`), `/sdd archive` — только для фазы проверки.
Плагин ничего не выполняет сам: команду запускает и подтверждает человек.

## Карта Impact

Если в `proposal.md` есть раздел `## Impact` со списком файлов, плагин сверяет
его с рабочим деревом:

- `link.impact-missed` — Impact перечисляет пути, но ни один изменённый файл
  под них не попадает;
- `link.untracked` — файл изменён вне Impact и без аннотации `@sdd`.

Правила включаются в фазе реализации и проверки, чтобы не шуметь на старте.

## Отчёт и CI

`/sdd report` и `node scripts/check.js <путь> --report` печатают markdown-сводку:
фаза, изменение, задачи, вопросы, цикл, архив, дрейф, аннотации, Impact и
замечания.

Для пайплайна: `node scripts/check.js . --ci` — код возврата 1 при
предупреждениях, `--fail-on error` — только при ошибках, `--json` — машинный
вывод. Без `--ci` код возврата всегда 0.

## Недельный дайджест

`/sdd digest [дней]`, `node scripts/check.js . --digest 7` и инструмент
`sdd_digest` собирают markdown-сводку за окно: сколько изменений
заархивировано и начато, коммиты с кодом и с артефактами, файлы вне
артефактов, медиана цикла, текущая фаза и замечания. Без git — честно пишет,
что история недоступна.

Автодоставку делает DSH-расписание: создай задачу с промптом вроде «Сделай
недельный SDD-дайджест проекта: вызови sdd_digest и пришли результат».
Плагин сам расписания не создаёт.

## Канбан задач

Вкладка «Задачи» показывает задачи активного изменения по колонкам
«Очередь / В работе / Проверка / Готово»:

- карточки — тикеты scratch (`**Status:**`) и чекбоксы OpenSpec;
- кнопки «Взять», «Проверка», «Готово», «Вернуть» меняют статус, переписывая
  **только** строку статуса или один чекбокс; остальной файл не трогается;
- у OpenSpec задачи бинарные, поэтому доступны только «Очередь» и «Готово»;
- те же действия доступны модели: `sdd_tasks` и `sdd_task_move`.

Плагин не держит вторую копию статуса: источник истины — сам артефакт.

## Команды и инструменты

`/sdd` — состояние, `/sdd next` — следующий шаг, `/sdd check` — замечания,
`/sdd docs` — документы, `/sdd stats` — статистика, `/sdd init` — создать
`.sdd/config.json`, `/sdd refresh` — пересчитать.

Модели доступны `sdd_status` (полное состояние проекта) и `sdd_check`
(только замечания).

## Системный промпт

В промпт попадает одна короткая строка: практика, фаза, изменение, задачи,
следующий шаг, правило фазы и до трёх документов. Строка меняется только
вместе с состоянием, поэтому кеш промпта не рвётся на каждом шаге. В начале
сессии модель один раз получает более подробную сводку.

## Настройка

Файл `.sdd/config.json` в проекте создаётся командой `/sdd init` и правится
руками: практика, активное изменение, порог устаревания, корни документации,
включение проверок и статистики.

Плагин только читает исходники. Единственная запись — `.sdd/config.json`, и
существующий файл не перезаписывается. Секреты не читаются, сетевых вызовов
нет.
